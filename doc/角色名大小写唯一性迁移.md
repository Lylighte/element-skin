# 角色名大小写唯一性迁移

## 背景与规则

Minecraft Services 名称查询需要与当前站点的大小写忽略查询一致。
旧数据库的 `UNIQUE(name)` 允许不同用户分别占用 `CasePlayer` 和 `caseplayer`，
使按名称读取无法唯一确定 UUID。

新规则保留名称的显示大小写，使用 `profiles_name_key ON profiles (lower(name))`
保证全站唯一。该索引同时服务单名和批量名称查询。所有写入路径共用此约束，
不通过查询排序选取冲突记录，也不新增重复的业务实现。

本次不改变角色名字符集、长度、UUID 生成方式或 UUID 持久化值。
同一角色的大小写调整不会改变用户、材质或身份。不会自动删除、合并或重命名旧角色。

## 升级检查

先备份数据库，在暂停站点和其他写入进程后检查冲突。以下查询只读：

```sql
SELECT lower(name) AS normalized_name,
       array_agg(id ORDER BY id) AS profile_ids,
       array_agg(name ORDER BY id) AS profile_names,
       array_agg(user_id ORDER BY id) AS owner_ids
FROM profiles
GROUP BY lower(name)
HAVING count(*) > 1
ORDER BY normalized_name;
```

没有结果时可以升级。启动初始化会在同一 schema 事务中移除旧的大小写敏感约束，
建立大小写忽略的唯一索引。重复初始化不会重复创建索引或修改角色数据。
索引创建需要扫描角色表，schema 初始化会持有表锁，应在维护窗口进行。

有冲突时先由维护者与角色所有者确认谁保留当前名称、谁使用新的唯一名称。
只修改已确认角色的 `name`，保留 `id`、`user_id`、`texture_model`、`skin_hash`、`cape_hash`。
修复名称之前，不要让采用新查询规则的站点继续对外提供服务。

确需直接修复数据库时，以下是参数化事务模板，包含写入动作，必须替换为已确认的数据：

```sql
BEGIN;
LOCK TABLE profiles IN SHARE ROW EXCLUSIVE MODE;
-- $1：已确认的新名称；$2：角色 UUID；$3：当前旧名称。
UPDATE profiles
SET name = $1
WHERE id = $2 AND name = $3
  AND NOT EXISTS (
      SELECT 1 FROM profiles p
      WHERE lower(p.name) = lower($1) AND p.id <> $2
  )
RETURNING id, user_id, name;
-- 必须恰好返回一行；否则回滚并检查参数，不要提交。
COMMIT;
```

确认新名称符合 `[A-Za-z0-9_]`、1–16 字符，再重复只读检查。
模板中的参数应通过 PostgreSQL 客户端绑定，不可原样粘贴为普通 SQL 执行。

## 失败边界

仍有冲突时，初始化返回包含冲突名称和修复提示的 PostgreSQL `23505` 错误，
站点启动失败。整个 schema SQL 事务回滚，旧唯一约束和全部角色数据保留。
修复后重启即可重试迁移；失败的初始化不会随机挑选一条角色继续启动。

数据库层保留唯一冲突标识 `profiles_name_key`，现有 service 将其映射为精确业务错误，
或由注册、导入候选名分配流程重试。正版绑定同步继续使用现有事务保存点处理名称冲突。

## 验证范围

回归测试覆盖跨用户创建、个人和管理员重命名、同一角色大小写调整、
注册事务失败不留下用户或消耗邀请码、并发创建与重命名、并发导入候选名重试、
正版角色同步名称冲突、协议查询别名和批量名称去重。

迁移测试覆盖无冲突升级、重复初始化、冲突启动失败、原约束与数据回滚、
人工修复后重试，以及修复后约束继续生效。
